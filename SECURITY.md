# Безопасность «Лоск»

Документ описывает модель угроз, реализованные контроли, результаты
самопентеста и чек-лист перед продакшеном.

Последний прогон: **72/72 проверки пройдены, 0 провалов, 0 критичных**
(production-сборка, `npm run pentest`).
Отчёты: `security/reports/pentest-*.json`.

---

## 1. Что защищаем

| Актив | Где | Последствия утечки |
|---|---|---|
| Телефоны, адреса, комментарии клиентов | `data/db.json` | Спам, угроза безопасности людей |
| Секретная ссылка заявки `/t/<token>` | URL | Полный доступ к чужой заявке |
| Ссылка на оплату `/pay/<token>` | URL | Доступ к платёжной странице чужого заявки |
| Аккаунт владельца | cookie `losk_sid` | Полный контроль над заявками и ценами |
| Платёжные записи и чеки | `db.payments` | Подмена статуса оплаты |
| Push-подписки | `db.pushSubs` | Спам на устройство |

## 2. Модель угроз (STRIDE, сокращённо)

| Угроза | Сценарий | Контроль |
|---|---|---|
| **S**poofing | Подбор пароля владельца | scrypt (N=16384), лимит 8 попыток / 10 мин на IP + 8/15 мин на e-mail, одинаковый ответ для «нет пользователя» и «неверный пароль», KDF выполняется всегда (анти-тайминг) |
| **T**ampering | Подмена цены заявки в запросе | Цена считается только на сервере из `lib/pricing.ts`; `zod` вырезает `estimate`, `quote`, `status` из тела |
| **T**ampering | Подмена payload вебхука | HMAC-SHA256 по канонической строке + `timingSafeEqual` + проверка `issuedAt` (±5 мин) + nonce-кеш |
| **R**epudiation | «Я не отправлял заявку» | `audit`-журнал и `timeline` с `clientVisible`, `ipHash` |
| **I**nformation disclosure | Утечка чужих заявок по ID | Доступ только по 192-битному токену; ID-перебор не работает; ответы 404 вместо 403 |
| **I**nformation disclosure | Токены/пароли в HTML | Проверено: в отрендеренном HTML нет `trackToken`, `payToken`, `passwordHash` (в dev-режиме RSC-отладка показывает больше — только локально) |
| **D**enial of service | Флуд заявками / перебор | Скользящее окно по IP на каждом маршруте, отдельные бакеты, штрафные блокировки |
| **E**levation of privilege | Обход CSRF/авторизации | Сессия + HMAC-CSRF + Origin/Referer, проверка роли на сервере в каждом обработчике |
| **XSS** | `<script>` в имени/комментарии | React экранирует вывод; имя ограничено алфавитом; комментарий хранится как текст; CSP без `unsafe-eval`, `object-src 'none'` |
| **Upload abuse** | Загрузка SVG/HTML/полиглота | Тип по magic bytes, allow-list JPEG/PNG/WebP/AVIF, размеры из заголовков (без декодирования пикселей), случайное имя на сервере |
| **Path traversal** | `../` в id файла | Регулярка на id и финальная проверка `path.resolve` внутри каталога uploads |
| **Replay** | Повтор вебхука | Кеш nonce + окно времени |

## 3. Реализованные контроли

### Транспорт и заголовки (`next.config.ts`)

- `Content-Security-Policy`: `default-src 'self'`, `object-src 'none'`,
  `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`,
  `connect-src 'self'`, `img-src 'self' data: blob:`, `upgrade-insecure-requests`.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy` (камера/микрофон/гео/платежи выключены),
  `COOP`, `CORP`, `X-Permitted-Cross-Domain-Policies: none`.
- `poweredByHeader: false` — никаких версий стека в ответах.
- `Cache-Control: no-store` на `/api/*` и `/admin/*`, `X-Robots-Tag: noindex` на кабинет.

### Аутентификация и сессии (`lib/auth.ts`)

- scrypt с солью 16 байт, параметры в самой строке хеша (апгрейд без сброса паролей).
- Токен сессии — 32 случайных байта; **на диске только SHA-256** от него.
- Cookie: `HttpOnly`, `SameSite=Lax`, `Secure` в продакшене, срок 7 дней,
  удаление серверной записи при logout (не только cookie).
- **Вторая cookie `losk_sig`** = HMAC(SESSION_SECRET, токен сессии). Edge-middleware
  проверяет пару до рендера и отклоняет подделанные/мусорные значения редиректом
  307. Это не замена проверке в БД, а защита от того, что `redirect()`, брошенный
  после начала стриминга, отдаётся как HTTP 200.
- `COOKIE_INSECURE=1` — только для локального демо по http, в README помечен как «убрать».

### CSRF (`lib/csrf.ts`)

Два независимых механизма:

1. Владелец: `x-csrf-token = HMAC(CSRF_SECRET, sessionId)` — stateless, привязан к сессии.
2. Анонимные формы: double-submit cookie `losk_csrf` (не HttpOnly, ставится middleware)
   + тот же заголовок.

Плюс проверка Origin/Referer для всех изменяющих методов.

### Валидация (`lib/validate.ts`)

- `zod`-схемы на каждый вход, `stripControl()` убирает управляющие символы.
- Телефон нормализуется к `+7XXXXXXXXXX`, имя — только буквы/пробел/дефис.
- `.default("")` + `.max(n)` на текстах; неизвестные ключи отбрасываются.
- Ограничение размера тела 200 КБ до парсинга.

### Загрузка файлов (`lib/media.ts`, `api/.../photos`)

- Тип определяется по magic bytes; `Content-Type` от клиента игнорируется.
- SVG отклоняется (XSS/XXE-вектор), расширение берётся из фактического типа.
- Размеры читаются из заголовков (JPEG SOF, PNG IHDR, WebP, AVIF ispe) —
  «бомба декомпрессии» не может положить сервер, потому что пиксели не декодируются.
- Имя файла — серверный `img_<random>`, оригинальное имя не используется.
- Отдача: `nosniff`, `Content-Security-Policy: sandbox`, `Content-Disposition: inline`.

### Права на медиа (`api/media/[id]`)

- Владелец с валидной сессией видит всё.
- Аноним — только фото из заявок с `photos.published = true`.
- Любой промах → `404` (нельзя перебором узнать, существует ли фото).

### Платежи (`lib/payments.ts`)

- Сумма берётся из согласованной сметы на сервере; клиент не может её указать.
- Идемпотентность через `idempotencyKey` (защита от двойного списания при двойном клике).
- Платёжный интент нельзя использовать с чужим `payToken`.
- Вебхук: HMAC + окно ±5 минут + nonce-кеш + сверка суммы **до** любых
  идемпотентных коротких путей.
- Карта: только Luhn-проверка в памяти обработчика, **не логируется и не пишется на диск**,
  сохраняются лишь последние 4 цифры. В продакшене заменяется hosted-checkout провайдера.

### Push

- Подписка владельца требует сессию + CSRF; подписка клиента — секретный токен заявки.
- Мёртвые endpoint'ы (404/410) автоматически удаляются.

### Ограничения частоты (`lib/ratelimit.ts`)

| Маршрут | Лимит |
|---|---|
| `POST /api/requests` | 10 / 10 мин + блок 10 мин |
| `POST /api/auth/login` | 8 / 10 мин + блок 15 мин (+ отдельный лимит по e-mail) |
| `POST /api/payments/*` | 12 / 10 мин; 6 попыток на конкретный платёж |
| `POST /api/track/find` | 5 / 10 мин + блок 20 мин |
| загрузка фото | 30 / 10 мин |

Ключ = `bucket + route + HMAC(IP)`; сырые IP в памяти не хранятся.

### Данные (`lib/db.ts`)

- Атомарная запись: temp-файл → `fsync` → `rename`. Обрыв процесса не оставит
  половину файла.
- Повреждённый JSON не затирается: сохраняется копия `db.json.corrupt-<ts>`.
- Файлы загрузок — `0o600`, каталог `data/` в `.gitignore`.

## 4. Найденные и исправленные уязвимости

Все находки получены реальным прогоном `scripts/pentest.mjs` и ручными проверками.

| # | Проблема | Влияние | Исправление |
|---|---|---|---|
| 1 | `z.discriminatedUnion` с опциями `ZodIntersection` падал при инициализации модуля | **HTTP 500 с HTML-страницей ошибки** на `PATCH /api/admin/requests/:id`; в dev — стектрейс, в prod — нерабочий кабинет | `.merge()` вместо `.and()` в схеме + `try/catch` возвращает JSON `{error}` вместо HTML |
| 2 | В `applyPaymentEvent` идемпотентный путь «уже оплачено» стоял **до** сверки суммы | Подписанное событие с изменённой суммой принималось молча (200) без сигнала об аномалии | Сверка суммы вынесена перед идемпотентным коротким путём |
| 3 | Поле-ловушка отбивалось как `422` с деталями валидации | Бот получал подсказку, какое поле «палит» | Ловушка вынесена в отдельную проверку → общий `400` без деталей |
| 4 | Service worker отдавал HTML из кеша при гонке с 3-секундным таймером | На медленном холодном старте показывались вчерашние цены | Навигации: network-first, кеш только как offline-фолбэк |
| 5 | Опубликованные фото не появлялись на главной до истечения ISR | Владелец публикует фото, а клиент их не видит | `revalidatePath("/")` в обработчике публикации |
| 6 | Лимит 5 заявок / 10 мин блокировал реальных клиентов за общим NAT | Ложные блокировки | Лимит 10 / 10 мин при сохранении honeypot/тайминга/CSRF |
| 7 | Сессионная cookie `Secure` ломала локальную проверку production-сборки | Невозможно проверить кабинет локально | Явный `COOKIE_INSECURE=1` для локального демо, задокументирован как «только разработка» |
| 8 | Скрытая ссылка на `/icons/favicon.ico` (404) | Лишний 404 в консоли | Удалена из метаданных |
| 9 | Подделанная cookie `losk_sid` отдавала `/admin` со статусом **200** вместо 307 | Redirect из Server Component после начала стриминга приходит как 200: данные не отдавались, но ответ выглядел как обход авторизации | Добавлена подписанная cookie `losk_sig` (HMAC) и проверка пары в Edge-middleware до рендера; при провале пара удаляется, ответ 307 |

Отдельно проверено и **не подтвердилось**:

- HTML-инъекция через имя/комментарий (React-экранирование + алфавитный фильтр имён).
- Подмена цены клиентом.
- Доступ к чужой заявке по ID без токена.
- Path traversal в `/api/media`, удалении фото и загрузке.
- Подделка/повтор/старение вебхука, неверная подпись, подмена суммы.
- Обход авторизации через middleware (middleware — только UX-редирект; реальные
  проверки в каждом обработчике).
- Прототип-загрязнение через JSON-тело.
- Утечка `passwordHash` / `trackToken` / `payToken` в отрендеренный HTML.

## 5. Остаточные риски и ограничения

Сознательные компромиссы — их нужно закрыть при выходе в продакшен:

1. **SQLite — один инстанс.** WAL держит много читателей и одного писателя;
   два процесса на одном файле работают, но не масштабируются горизонтально.
   Схема нормализована, поэтому переезд на Postgres — замена драйвера в
   `lib/db.ts` (`all/get/run/tx`) и синтаксиса миграций, а не переписывание кода.
2. **Rate limit и очередь логина — в памяти процесса.** При нескольких
   инстансах или serverless — Redis (`hit()` — единственная точка).
3. **IP определяется по `x-forwarded-for` только при `TRUST_PROXY=1`.**
   Иначе за прокси все клиенты делят один бакет.
4. **Секретный токен в URL.** Токен заявки/оплаты — единственный фактор доступа.
   Он не попадает в Referer (страницы `noindex`, `Referrer-Policy` ограничен),
   но при пересылке ссылки в мессенджере она может остаться в истории.
   Для повышения стойкости можно добавить подтверждение по SMS-коду.
5. **Восстановление доступа по коду + телефону.** Защищено лимитом 5/10 мин и
   одинаковым ответом на промах, но это weaker-proof, чем ссылка.
6. **Платёжный sandbox.** Реальные карты не списываются и не сохраняются;
   переход на ЮKassa/Stripe требует hosted-checkout, чтобы карта вообще не
   касалась нашего сервера.
7. **Демо-режим — это дыра по замыслу.** `DEMO_MODE=1` даёт любому посетителю
   кабинет владельца в один клик (`/api/demo/login`), просмотр заявок, смет и
   сброс данных. Это осознанный выбор для показа сайта клиенту: маршруты
   отвечают `404` при `DEMO_MODE=0`, кнопки не рендерятся, каждый вход пишется
   в аудит. **Перед публикацией на реальном домене `DEMO_MODE` обязан быть `0`**,
   иначе персональные данные клиентов (телефоны, адреса) доступны публично.
8. **CSP со `'unsafe-inline'` для скриптов.** Ограничение Next.js App Router
   (inline bootstrap). Строгий вариант — nonce-based CSP через middleware;
   не включён, потому что требует генерации nonce на каждый запрос и
   динамического рендера всех страниц (теряется статика и ISR).
9. **Нет подтверждения e-mail / 2FA владельца.** Для одного аккаунта в MVP
   достаточно; в проде рекомендуется TOTP.

## 6. Чек-лист перед продакшеном

- [ ] **`DEMO_MODE=0`** (иначе кабинет владельца открыт всем в один клик)
- [ ] `NEXT_PUBLIC_SITE_URL` = реальный домен (canonical, OG, ссылки в push)
- [ ] Сгенерировать новые `SESSION_SECRET`, `CSRF_SECRET`, `PAYMENT_WEBHOOK_SECRET`
- [ ] Задать сильный `ADMIN_PASSWORD`, включить `Secure`-cookie (убрать `COOKIE_INSECURE`)
- [ ] Настроить бэкап `data/losk.db` (WAL: `sqlite3 .backup`)
- [ ] Включить HSTS на балансировщике (приложение не ставит — за TLS-терминацией)
- [ ] `TRUST_PROXY=1` + корректные заголовки от прокси
- [ ] Postgres + Redis, если планируется больше одного инстанса
- [ ] Подключить реальный платёжный провайдер и его формат вебхука
- [ ] Настроить сбор логов и алерт на `audit`-события `auth.login.failed`
- [ ] Прогнать `npm run pentest` против staging-домена
- [ ] Проверить `/robots.txt`, `/sitemap.xml`, `/privacy`, `/offer`

## 7. Как воспроизвести проверку

```bash
npm run build
COOKIE_INSECURE=1 npm start        # локально, только для http://localhost

# в другом терминале
npm run seed                        # если данных ещё нет
npm run pentest                     # 59 проверок, exit code 1 при провале
BASE_URL=https://staging.example npm run pentest
```

Сьют работает по HTTP как чёрный ящик (заголовки, CSRF, авторизация, IDOR,
загрузки, вебхуки, rate limit, XSS) и читает `data/db.json` только для того,
чтобы получить реальные токены и подписать валидное событие «от провайдера».
